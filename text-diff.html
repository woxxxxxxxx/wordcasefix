Comparison method and interpretation guide

Text Diff compares two supplied versions and highlights additions, removals, and unchanged material. It is a review aid, not a version-control system and not proof of authorship. The usefulness of a diff depends on the comparison unit: line-oriented output is easy to scan for documents and code, but a wrapped or reformatted paragraph can appear more different than its meaning suggests.

Methodology

  1. Each input is normalized only as required by the interface, then divided into comparison units.
  2. The comparison algorithm finds an ordered sequence of matching units and marks units present only on the left as removed and only on the right as added.
  3. Unchanged sections provide context so a reviewer can locate edits without reading both documents from the beginning.
  4. The original text is not overwritten. Copy or save the reviewed version separately after checking every highlighted block.

Worked review example

If version A contains “Payment is due in 30 days” and version B contains “Payment is due in 15 calendar days,” the changed line should be reviewed as a substantive timing change. If the same paragraph is merely wrapped at a different column width, a line comparison may highlight several lines even though the words are nearly identical. Normalize formatting first when the goal is semantic review.

Test coverage and expected behavior

Test coverage includes identical input, a single inserted line, a single deletion, moved text, empty sides, Unicode characters, and line-ending differences. Manual verification covers short cases where the expected added and removed lines are unambiguous. Large documents should still be reviewed in their source application.

Decision checklist before using the output

Define what kind of change matters before comparing. A line diff is effective for configuration files, clauses, and structured drafts where line breaks are stable. It is less effective after automatic wrapping, OCR, or a formatter has rearranged the document. If formatting noise dominates, normalize line endings and agreed whitespace first, but retain an untouched copy so meaningful spaces are not lost. Review deletions before additions because removed qualifiers, dates, units, and negations are easy to miss. Then inspect numbers, names, URLs, obligations, and modal verbs such as must, may, and should. A clean diff does not prove two rendered files are equivalent: fonts, formulas, tracked comments, hidden spreadsheet cells, and document metadata can sit outside plain text. Use the original application’s review features for contracts, code merges, or regulated records when those layers matter.

Important limitations

  • Moved text can appear as a deletion plus an insertion.
  • Line-oriented comparison does not determine whether wording has the same legal or technical meaning.
  • Whitespace-only changes can create noise unless normalized deliberately.
  • Do not paste confidential documents into a web tool unless your organization permits browser-based processing.
